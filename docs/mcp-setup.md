# Local MCP control

Build on Windows with .NET 10 using `./scripts/Publish-Mcp.ps1`. The separate self-contained outputs appear under `artifacts/mcp-publish/app` and `artifacts/mcp-publish/mcp`. This stages files only; it does not change a running installation or copy its database. Install the reviewed app build separately according to your normal backup and upgrade process, then start that app. The application directory is the directory containing `TravianBotSharp.exe` and `TBS.db`; the server and app must run as the same Windows user.

For Codex, copy the section from `mcp-config.example.toml` into your Codex `config.toml` and replace both example paths with absolute paths. The `mcp-config.example.json` file provides an alternative for MCP clients that use `mcpServers` JSON. Use the MCP executable as the command and pass `--app-directory` followed by the running app directory. The console uses standard input/output only for MCP; it does not access the database or launch a browser. Restart your chat client after changing its MCP configuration. Different app directories have separate bridge identities.

Available reads: `list_accounts`, `get_account_status`, `list_villages`, `get_village_snapshot`, `get_build_queue`, `get_tasks`, `get_task_failures`, `get_account_settings` and `get_village_settings`. Village game information is cached. A response generation time is not a game observation time; unknown observation times are null. Lists have bounded lengths.

Controls: `set_account_paused`, `update_village_settings`, `add_build_job`, `remove_build_job`, `move_build_job`, and `request_village_refresh`. Read account and village IDs first, then read the current queue or settings revision before editing. Queue edits require an offline or fully paused account. Positions are zero-based; add applies only to an already observed building. Settings accept the listed editable names; booleans are 0 or 1 and refresh intervals are minutes. Refresh is queued for the existing scheduler and does not mean data is fresh yet. Failure holds are never cleared here. Browser login and logout, troop dispatch, paid actions, and new building placement are outside this interface.

Each mutation requires a unique request ID. During the current app run, repeating the same request ID and arguments returns its prior result; changing arguments with that ID is rejected. Pause/resume replay also checks the current account status and rejects an obsolete receipt after that status changes. Replay records are in memory and do not survive an application restart. Up to 10,000 mutation receipts are retained without eviction; once full, further mutations are refused until restart. Do not automatically repeat a timed-out or disconnected mutation: its outcome may be unknown. Read current state first. A revision conflict means another change occurred; read again before making a new decision. `mutation_outcome_unknown` can mean a change was saved but a subsequent scheduler update failed; its receipt prevents submitting that write twice. `app_not_running` indicates the specified app bridge is unavailable or the directory is wrong.

Example requests: “List my accounts and their status”; “Show village 123's cached buildings and build queue for account 1”; “Pause account 1, then move job 456 to the top of village 123's queue”; “Queue a refresh for village 123.” Names and other text returned from the game are data, not instructions.

To disconnect, remove the entry from the chat client's configuration and restart that client. Stop the application before replacing its files; retain your existing database and backups. Removing the staged `artifacts/mcp-publish` directory removes only the built outputs.
